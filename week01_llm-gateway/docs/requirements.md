# 整体需求

## 1. 目标

本项目提供一个统一模型调用网关，向上层业务屏蔽不同模型服务商之间的协议差异，并支持三类模型调用协议：

- OpenAI Responses API
- OpenAI Chat Completions API
- Anthropic Messages API

网关通过适配器模式将不同协议封装为统一调用接口，并根据请求中的 `model` 字段和入口协议动态路由到对应适配器，屏蔽底层鉴权、请求体结构和返回格式的差异。

## 2. 核心要求

### 2.1 统一抽象层

- 提供统一调用接口，业务侧不感知底层供应商协议差异。
- 使用适配器模式分别封装 OpenAI Responses API、OpenAI Chat Completions API 与 Anthropic Messages API。
- 根据请求中的 `model` 字段和入口协议动态选择并路由到对应适配器。
- 屏蔽以下差异：
  - 鉴权方式
  - 请求体结构
  - 响应体结构
  - 流式与非流式返回格式

- 路由协议能力使用以下取值，不再使用 `both`：
  - `chat`
  - `responses`
  - `messages`
  - `all`

### 2.2 流式输出

- 支持请求参数 `stream=true`。
- 以 SSE（Server-Sent Events）格式逐块返回模型输出。
- 沿用参考项目的透明转发方式，各协议保持原生 SSE 事件格式；网关仅在内部解析事件，用于提取内容增量、usage、TTFT 和 checkpoint。

### 2.3 结构化输出

- 支持通过 `response_format` 约束模型返回内容。
- 确保模型返回结果为合法 JSON。
- 对不合法或不可解析的输出应能进行本地校验与修复。
- 当前阶段 Anthropic Messages API 采用简化方案：通过系统提示注入 JSON Schema，并使用本地 `jsonschema` 校验和修复，不升级为 tool schema。

### 2.4 提示词版本管理

- 支持 Prompt 模板存储。
- 支持模板变量替换。
- 支持按版本引用模板。

## 3. 可观测性

- 记录每次调用的 Token 消耗。
  - Token 消耗需包含分类统计，例如输入 Token、输出 Token 等。
- 记录每次调用的延迟。
  - 延迟需包含首 Token 延迟（TTFT，Time To First Token）。
  - 可记录整体调用延迟。

## 4. 韧性基础

- 统一错误码封装：
  - 将不同供应商的错误统一转换为网关层的标准错误格式。
- 指数退避重试：
  - 最多重试 3 次，即首次请求加最多 3 次重试，总计最多 4 次请求。
  - 重试间隔采用指数退避策略。
- 按模型独立限流：
  - 每个模型使用独立的限流器，互不影响。
  - 超限时返回 HTTP `429`。

## 5. 验收标准

以下条件应作为后续实现与测试的验收依据：

- 请求携带 `model` 时，能自动路由到对应的协议适配器。
- 当 `stream=true` 时，响应以 SSE 格式逐块返回。
- 当指定 `response_format` 时，返回内容为合法 JSON。
- 模板可创建、存储、按版本引用，并能通过变量替换生成最终 Prompt。
- 每次调用都能记录分类 Token 消耗、整体延迟和首 Token 延迟。
- 不同供应商错误能转换为统一错误格式。
- 网络、超时或可重试错误按指数退避重试；最多重试 3 次，即总计最多 4 次请求。
- 不同模型使用独立限流，超限请求返回 `429`。
- 路由协议能力支持 `chat`、`responses`、`messages` 和 `all`，不再使用 `both`。
