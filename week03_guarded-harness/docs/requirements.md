## 2. 背景与目标

本项目要在不重写 `smolagents` 核心的前提下，为 `ToolCallingAgent` 增加一层可恢复的
Guarded Coding Harness。

职责边界如下：

- **模型负责决策**：理解任务、规划步骤、选择工具、提交工具参数、产生候选最终回答。
- **程序负责约束和事实**：参数与权限门禁、执行隔离、状态持久化、审计、恢复、预算和最终验收。
- **不信任模型输出**：模型不能自行授予权限、修改审批结果、定义成功标准，或通过自述证明任务完成。

项目必须让 Agent 能安全完成两类仓库任务：

1. **代码理解**：阅读目标仓库，形成有代码依据的说明文档，不修改源码。
2. **测试修复**：运行测试、定位失败原因、修复源码，并在允许时补充测试，最终取得可复验的通过结果。

成功标准不是“模型生成了合理回答”，而是：工作区状态、验收命令结果和 append-only 审计共同证明
任务交付物确实存在且符合任务约束。

## 3. 范围与非目标

### 3.1 首期范围

- 单个 Agent Run 绑定一个目标仓库根目录。
- `ToolCallingAgent` 的原生决策循环继续工作。
- 仓库读取、文件写入、按白名单启动命令、测试执行和 git 状态读取。
- 两类任务的配置化验收：代码理解、测试修复。
- 单机、本地、可离线复现的正常执行、审批等待、失败停止和进程恢复。
- Fake Model 驱动的确定性自动化测试。

### 3.2 非目标

- 不实现通用自主编程平台、多仓库并行调度、分布式任务队列或 Web 管理界面。
- 不提供无限制 shell、包安装、后台常驻进程或任意网络访问。
- 不替代 smolagents 的模型调用、消息管理和 ReAct/Tool Calling 循环。
- 不通过提示词、回调日志或模型最终回答充当安全门禁。
- 不对非幂等外部副作用承诺物理上的 exactly-once；无法确认结果时必须暴露“不确定”状态并停止自动重放。

## 4. 核心原则

1. **单一运行入口**：除模型本身外，所有任务装配、工具治理、状态流转、恢复和完成判定都从
   `Harness.run()` 或其唯一公开等价入口进入。
2. **执行前门禁**：任何有权执行 handler 的路径都必须在执行前重新校验参数、权限、风险、审批和重复调用。
3. **失败关闭**：校验、权限、审批、状态、审计或验收基础设施异常时默认拒绝，不得默认放行。
4. **事实与意图分离**：模型报告是意图或声明；状态、审计、工作区 diff 和验收命令结果是程序事实。
5. **最小权限**：工具、路径、命令、环境变量、输出和预算都使用窄范围 allowlist，不以黑名单作为唯一边界。
6. **可恢复而非盲目重放**：恢复从最后一个安全步骤继续；结果未知的副作用不自动重复。

## 5. 总体运行流程

```text
任务配置 + 目标仓库 + Fake/Real Model
                │
                ▼
          Harness.run()
                │
                ▼
       ToolCallingAgent 决策循环
                │ ToolCall(tool_call_id, name, args)
                ▼
        ┌─────────────────┐
        │ Gate 唯一执行入口 │
        └─────────────────┘
           │    │      │
           │    │      └── 拒绝：结构化错误，handler 不执行
           │    └───────── 审批：等待、批准、拒绝或过期
           ▼
        Sandbox 边界检查
           │
           ▼
       记录“即将执行”
           │
           ▼
        执行 handler
           │
           ▼
       执行结果/证据/预算更新
           │
           ▼
       安全边界 Checkpoint
           │
           ▼
        模型继续决策或产生候选最终回答
                │
                ▼
        独立完成检查（Completion）
                │
                ▼
       accepted / rejected / stopped / failed
```

执行状态与验收结论必须分开表示。例如 `completed` 只表示运行流程结束，不表示交付物已通过验收；
`accepted` 必须另有工作区和审计证据。

## 6. 功能需求

### 6.1 smolagents 集成与 Harness 装配

**REQ-HARNESS-001（必须）**
必须使用 `smolagents.ToolCallingAgent` 及其公开扩展点完成模型决策和工具调用循环。不得复制
Agent 核心、修改 site-packages、猴子补丁私有方法，或以另一套循环替代 smolagents。

**REQ-HARNESS-002（必须）**
`harness.py` 必须负责装配模型、工具、Gate、Sandbox、State Store、Checkpoint、Audit 和 Completion Checker，
并向调用方提供一个明确的运行入口。CLI、测试和程序化调用不得各自拼装一套缺少安全组件的执行链。

**REQ-HARNESS-003（必须）**
任务级业务规则必须位于任务配置、Gate、Sandbox、Completion 或独立策略模块中，不得散落在文件、
命令等 handler 内。handler 只负责在边界通过后完成单一实际操作。

**REQ-HARNESS-004（必须）**
每个 Run 必须绑定 `run_id`、任务类型、目标工作区、配置指纹和预算。切换任务或工作区必须创建
新的 Run，不能复用上一任务的审批、证据或验收结论。

**REQ-HARNESS-005（必须）**
Harness 必须保证 `ToolCallingAgent` 产生的每个工具调用都进入统一治理路径。若模型并行提交多个调用，
写文件、启动进程和审批相关操作必须串行化；只读并发也必须有数量、预算和审计顺序约束。

### 6.2 Gate：唯一工具执行入口

**REQ-GATE-001（必须）**
`gate.py` 必须是所有 Tool Call 的唯一执行入口。调用方只能提交候选 `tool_call_id`、工具名和参数；
Gate 通过后才能触达 handler。已批准操作再次执行时也必须经过 Gate 复核，不能借审批记录绕过门禁。

**REQ-GATE-002（必须）**
Gate 必须在 handler 执行前按固定顺序完成以下检查：

1. 工具存在且在当前 Agent/任务可见；
2. 参数符合 schema，拒绝未声明字段；
3. 语义约束成立，例如路径格式、非空修改、可分页/可搜索参数边界；
4. 当前角色、任务和模式具备相应读、写、执行权限；
5. 风险等级和执行模式允许操作；
6. 审批要求已满足，且审批与本次参数和执行上下文一致；
7. 相同工具和规范化参数没有超过重复调用预算；
8. 总轮数、工具调用数、时间和令牌/成本预算仍允许继续。

前面的拒绝条件不能被后续 allow 规则覆盖。具体错误码可以扩展，但必须稳定、可审计、可反馈给模型。

**REQ-GATE-003（必须）**
任何拒绝都必须发生在 handler 之前，并返回结构化错误，至少包含原始 `tool_call_id`、稳定错误码、
人类可读原因和拒绝阶段。拒绝不得伪造成功结果，也不得触发任何仓库或外部副作用。

**REQ-GATE-004（必须）**
审批必须绑定工具名、规范化参数、目标工作区、`run_id` 和任务。审批只能成功消费一次；
参数、工作区、任务或运行变化后必须重新审批。审批缺失、过期、通道不可用或状态损坏时必须拒绝。

**REQ-GATE-005（必须）**
重复调用检查必须使用规范化后的工具名与参数，能拦住等价参数重复和模型循环调用，同时允许
任务明确需要的有限重复读取。连续重复不允许耗尽预算或产生重复写入。

### 6.3 Sandbox：路径、命令和进程边界

**REQ-SANDBOX-001（必须）**
`sandbox.py` 必须将文件访问限制在本次目标工作区。相对路径必须解析到工作区内的规范化路径；
必须拦截 `..` 逃逸、绝对路径越界、符号链接逃逸和等价路径绕过。对不存在的目标路径，至少展开
最近已存在祖先后再判断包含关系。

**REQ-SANDBOX-002（必须）**
必须支持按任务区分的 `deny_read`、`deny_write` 和窄范围 `allow_write`：

- 敏感文件默认不可读，包括 `.env`、密钥、令牌和凭据文件；
- `.git/`、依赖目录、任务声明的基础配置文件默认不可写；
- 测试修复中的已有测试默认只读，只有显式允许的目录可新增测试；
- allow 例外不能放宽平台级敏感路径限制。

**REQ-SANDBOX-003（必须）**
命令执行必须使用 argv 数组和 `shell=False`，可执行文件及测试命令必须来自可信任务配置或固定 allowlist。
模型不能通过参数自由指定 shell、解释器包装、命令分隔符、重定向或可执行路径来绕过命令规则。

**REQ-SANDBOX-004（必须）**
子进程必须固定 `cwd` 到目标工作区，使用经过筛选的最小环境变量，过滤 API Key、Token、Secret、
Password 等凭据，并设置执行超时、输出采集上限和进入模型上下文前的输出裁剪。

**REQ-SANDBOX-005（必须）**
超时必须真实终止子进程组；返回结果必须明确包含退出码或信号、是否超时、是否截断和已采集输出。
非幂等命令超时后必须标记结果不确定，不得自动重试或判定成功。

**REQ-SANDBOX-006（必须）**
任何越界路径、敏感文件、未授权命令、超时或输出超限都必须在真实执行层被拦截或截断，不能只靠
系统提示词提醒模型。

### 6.4 State Store：业务状态

**REQ-STATE-001（必须）**
`state_store.py` 必须持久化 Run 的完整业务状态，至少包括：

- `run_id`、任务类型、任务说明、目标工作区、配置指纹和生命周期时间；
- 当前状态、计划、已执行步骤和当前步骤；
- 每次工具调用的名称、规范化参数、结果、证据和错误；
- 预算及已用量，包括轮数、工具调用数、Token/成本或等价资源额度；
- 审批请求、决定、消费者和有效期；
- 停止原因、最终回答和完成检查结论。

**REQ-STATE-002（必须）**
Run 完成、失败、等待审批或中断后，必须能重新打开存储并读取完整业务状态。关键状态更新必须原子化，
不能因单条日志损坏导致已执行步骤和审批状态自相矛盾。

**REQ-STATE-003（必须）**
State Store 记录“业务当前状态”，Audit 记录“发生过什么”，两者职责不能合并。必要关联统一使用
`run_id`、`step_id`、`tool_call_id` 和 `approval_id`。

### 6.5 Checkpoint：安全恢复

**REQ-CHECKPOINT-001（必须）**
`checkpoint.py` 必须在安全步骤边界创建可恢复快照。安全边界至少包括：模型步骤完成、工具调用完成、
工具明确失败、审批状态落定，或完成检查结束。

**REQ-CHECKPOINT-002（必须）**
恢复必须由新进程完成：能够读取历史 Run、计划、步骤、证据、预算、审批和停止原因，并从最后一个
已确认的安全边界继续 Agent 循环。恢复过程不得依赖原进程内存、原模型对象或未持久化的临时状态。

**REQ-CHECKPOINT-003（必须）**
已完成且已有确定结果的写操作不得重复执行。Checkpoint 必须与 State Store、Audit 和审批消费状态
一致；原子提交前崩溃时，新进程必须能识别“尚未执行”或“结果未知”，不能直接重放非幂等副作用。

**REQ-CHECKPOINT-004（必须）**
恢复前必须重新校验工作区身份、配置版本、参数指纹和审批有效期。工作区或配置已改变时拒绝继续，
要求人工处理或启动新 Run。

### 6.6 Audit：append-only 事实账本

**REQ-AUDIT-001（必须）**
`audit.py` 必须以 append-only 方式记录事件，不允许修改或删除既有业务审计记录。至少覆盖：

- Run 开始、恢复、停止和完成；
- Gate 放行与拒绝；
- 审批请求、批准、拒绝、过期和消费；
- 工具执行开始、成功、失败、超时和结果不确定；
- Checkpoint 安全落盘；
- 最终验收通过或拒绝。

**REQ-AUDIT-002（必须）**
必须能按 `run_id` 和 `tool_call_id` 还原完整决策链：模型提交了什么、Gate 为何允许或拒绝、
谁批准了什么参数、handler 是否执行、执行结果是什么、Checkpoint 是否落盘、最终如何验收。
审批与结果必须能通过 `approval_id` 关联。

**REQ-AUDIT-003（必须）**
审计记录必须包含稳定事件类型、时间、状态、错误码、关联 ID 和必要参数/结果摘要。敏感字段必须在
落盘和返回模型前脱敏；不得记录 API Key、令牌、密码或敏感环境变量原值。

**REQ-AUDIT-004（必须）**
计划执行任何副作用前，必须成功写入执行意图；执行后必须写入确定结果。审计写失败时不得继续执行新的
副作用；若副作用已经发生但结果未能持久化，必须标记为不确定并停止自动恢复。

### 6.7 任务配置与两类任务

**REQ-TASK-001（必须）**
不同任务的工作区、允许/禁止路径、工具权限、测试命令、交付物、预算、审批和验收条件必须由经过校验的
任务配置声明。核心 Gate、Sandbox 和 Harness 不得散落 `understand`、`fix_tests` 等任务名分支。

**REQ-TASK-002：代码理解（必须）**

- Agent 可以读取允许范围内的源码、测试、配置和仓库状态。
- 只允许写入任务声明的说明文档交付物，不得修改目标仓库源码。
- 文档必须至少包含调用链或关键逻辑说明、涉及文件和行号引用，并区分事实与推断。
- Completion 必须校验交付物路径、非空内容、引用可解析，以及工作区 diff 没有越界修改。

**REQ-TASK-003：测试修复（必须）**

- 开始修复前必须记录测试命令、基线结果和工作区初始状态。
- Agent 必须结合失败输出阅读相关测试与实现，修复源码根因，不能只改测试让断言变绿。
- 已有测试默认不可修改、删除、跳过或弱化；只有配置明确允许的目录可以新增测试。
- 修复后必须用同一验收命令复跑，并以实际退出码和测试报告判定结果。
- Completion 必须检查最终测试结果和 diff 范围，拒绝越界修改或减少测试覆盖。

**REQ-TASK-004（必须）**
模型在最终回答中声称“文档已写入”“测试已全绿”或“任务已完成”，不得单独作为交付证据。
Completion Checker 必须基于实际文件、工作区 diff、审计和测试执行结果判定，并显式区分：

- 运行是否结束；
- 交付物是否存在；
- 验收是否通过；
- 模型是否存在无证据声明。

### 6.8 Completion：最终验收

**REQ-COMPLETE-001（必须）**
Harness 必须在 Agent 停止后调用模型之外的 Completion Checker。模型不得自定义、跳过或覆盖验收结果。

**REQ-COMPLETE-002（必须）**
Completion 必须为每个 Run 输出结构化结论，至少包含 `accepted`、验收项、证据路径/审计 ID、
失败原因和完成时间，并把结论同时写入 State Store 与 Audit。

**REQ-COMPLETE-003（必须）**
验收命令缺失、不可执行、超时、结果未知、交付物不存在、diff 越界或审计链不完整时，不得判定为
`accepted`。

## 7. 必须交付物

以下文件是作业明确要求的交付边界。Python 模块应位于可由 `src` 布局导入的包内，推荐包目录为
`src/guarded_harness/`；测试文件路径必须保持下表所列名称。

| ID | 必须交付 | 最低职责 | 验收证据 |
| --- | --- | --- | --- |
| DEL-001 | `gate.py` | 所有 Tool Call 的唯一入口；执行前完成参数、权限、风险、审批和重复动作检查 | 拒绝调用不进入 handler，返回结构化错误和原 `tool_call_id` |
| DEL-002 | `sandbox.py` | 限制文件路径、敏感目录、命令白名单、超时、环境变量和输出边界 | 越界路径、危险命令、超时进程均被真实拦截 |
| DEL-003 | `state_store.py` | 保存 Run、计划、步骤、证据、预算、审批和停止原因 | Run 完成或中断后能读取完整业务状态 |
| DEL-004 | `checkpoint.py` | 在安全步骤边界保存和恢复状态 | 新进程 resume 后继续执行，不重复已完成写入 |
| DEL-005 | `audit.py` | append-only 记录放行、拒绝、审批、执行和结果 | 可按 `run_id`、`tool_call_id` 还原决策链 |
| DEL-006 | `harness.py` | 装配模型、工具、Gate、Sandbox、State、Checkpoint、Audit 和完成检查 | Agent 只有一个运行入口，业务规则不散落在 handler |
| DEL-007 | `tests/` | 使用 Fake Model 覆盖正常路径和失败路径 | `pytest -q` 全绿，不依赖真实模型即可复现全部边界 |

## 8. 非功能需求

### 8.1 安全

- 默认离线运行；测试不得依赖真实模型、真实外部服务或用户凭据。
- 所有敏感信息在写入状态、审计、日志或模型上下文前脱敏。
- 所有安全判定必须位于程序执行路径，不能仅写在系统提示词或工具 description 中。
- 安全基础设施异常按失败关闭处理。

### 8.2 可恢复性与一致性

- State Store、Checkpoint、Audit 和审批消费必须有清晰的事务边界和一致性策略。
- 恢复操作必须幂等；重复 resume 不能重复已确认的工具调用。
- 无法确认是否已执行的非幂等操作必须进入 `unknown`/人工复核状态。

### 8.3 可测试性与可观测性

- 默认 pytest 必须可离线、快速、确定地重复执行。
- 测试使用隔离的临时工作区、临时数据库和 Fake Model，不污染开发者仓库。
- 每个拒绝、审批、执行、恢复和验收结果都有稳定错误码和关联 ID。
- 面向模型的错误摘要要有界、可行动，并指出错误阶段和修正方向。

### 8.4 代码质量

- 遵循 PEP 8 和 PEP 257，公共接口提供类型标注。
- 使用 Ruff 执行 lint 和格式检查。
- 依赖通过 pyenv 管理的 Python 环境安装，pip 与 `requirements.txt` 为依赖来源。
- 不引入与 smolagents 核心重复的第二套 Agent Loop。

## 9. 整体验收标准

项目只有同时满足以下条件才算完成：

1. 六个必须模块均已实现，并通过公共入口完成端到端装配。
2. `ToolCallingAgent` 决策循环保留；所有工具调用经过 Gate，安全逻辑不依赖模型自觉。
3. 参数、权限、风险、审批、重复调用和预算门禁均有拒绝路径测试，拒绝时 handler 执行次数为 0。
4. Sandbox 能真实拦截路径、敏感文件、非白名单命令、超时和输出越界，并移除子进程敏感环境变量。
5. 完成或中断后能读取完整业务状态；新进程能从 Checkpoint 恢复且不重复已完成写入。
6. Audit 为 append-only，能按 `run_id` 与 `tool_call_id` 重建决策链。
7. 代码理解和测试修复都由程序独立验收；模型自述不能替代产物、diff、退出码和审计证据。
8. 六个指定测试文件存在并覆盖对应边界，`pytest -q` 全绿。
9. 测试不需要真实模型即可复现正常路径和失败路径。
10. Ruff、格式检查和测试命令通过，文档与实际行为保持一致。

## 10. 后续设计需明确的实现决策

以下内容属于设计阶段，不改变本需求中的强制边界：

- State Store 与 Checkpoint 使用 SQLite、文件快照还是组合方案，以及事务提交顺序。
- smolagents 的具体公开兼容层类型、版本范围和工具包装方式。
- 任务配置格式、审批交互方式、CLI 参数和 Real Model Provider。
- 代码理解交付物的固定路径，以及引用行号的具体校验强度。
- 测试修复中“新增测试目录”“隐藏验收命令”和各工具预算的默认值。

这些决策应写入 `docs/design.md` 和 `docs/decisions.md`，并通过 `docs/test-plan.md` 明确验证方式。
