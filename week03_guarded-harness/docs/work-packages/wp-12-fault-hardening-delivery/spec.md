## 2. 目标

WP-12 必须把已经分别验收的治理能力组合成可复验的 P0 最终交付，并证明以下事实：

1. 代码理解和测试修复两类任务能通过统一 Harness/CLI 链路完成，而不是由测试直接伪造完成态。
2. Fake Model 驱动的端到端运行保留原生 `ToolCallingAgent` 决策循环，所有仓库副作用经过 Gate。
3. 写操作在审批前不产生文件变化；审批后跨进程 resume 最多执行一次。
4. 进程终止、审计失败、数据库锁冲突、Checkpoint 损坏和租约冲突都有确定性故障场景。
5. `UNKNOWN_RESULT` 不被自动重放，已确定写入不重复，预算、调用计数和步骤计数不清零。
6. 两类正式样例配置由项目正式配置加载器校验，并使用可复现的样例工作区。
7. 六个必须测试文件存在且承担设计映射规定的覆盖；额外测试不能替代这六份文件。
8. 全量 P0 场景可离线、确定、重复执行，不依赖真实 Provider、网络或用户凭据。
9. 需求、设计、决策、工作包、测试、验收场景和实际证据形成可追溯矩阵。
10. 运维文档说明运行、审批、恢复、状态库、日志、退出码、平台限制和禁止操作。
11. 根目录 `README.md` 只作为交付入口，准确区分计划、已实现能力和剩余风险。
12. 最终 `acceptance-report.md` 依据实际复跑证据给出 `accepted`、`rejected` 或 `blocked`，
    不以计划预期、模型最终回答或单个 happy-path 测试代替验收。

## 3. 准入、范围与非目标

### 3.1 准入条件

实现开始前必须同时满足：

1. WP-00 至 WP-11 的 `acceptance-report.md` 状态均为 `accepted`；
2. WP-00 至 WP-11 没有仍未关闭的 P0 缺陷、未解释 skip 或契约冲突；
3. 当前全量测试、Ruff lint 和 Ruff format check 有可复现绿色基线；
4. `docs/work-packages/index.md` 与实际工作包状态一致；
5. 本规格经需求方评审并冻结；
6. `plan.md` 基于冻结规格批准。

依赖未满足时，只允许文档初始化、只读接口探查、测试方案设计和无生产副作用的技术验证。
不得把 WP-12 文档中的计划行为写成“已实现”，不得以 WP-12 的端到端测试替代上游包内验收。

### 3.2 范围内

- 新增测试专用故障注入辅助设施和跨边界恢复测试；
- 扩展六个必须测试文件中的项目级场景；
- 新增两类任务的正式 YAML 样例配置；
- 按待确认决策提供样例工作区或明确的外部工作区绑定向导；
- 新增 `docs/test-plan.md` 和 `docs/operations.md`；
- 更新根 `README.md`、`docs/README.md`、`docs/work-packages/index.md` 和任务拆解链接；
- 汇总需求、决策、工作包规格、飞书核心验收、测试和证据映射；
- 执行两类 Fake Model 端到端任务、故障矩阵、全量测试、lint 和格式检查；
- 生成 WP-12 `acceptance-report.md`。

### 3.3 非目标

- 不新增 P0 运行时功能、工具、任务类型、migration 或后门；
- 不实现真实模型 Provider、API Key 管理、网络 smoke test 或模型质量评估；
- 不把飞书 P1 场景或真实模型场景改写成 P0 成功前置条件；
- 不实现隐藏验收、多仓库、分布式执行、容器/虚拟机级隔离或 Windows 进程组支持；
- 不通过修改已有 migration、审计事实或历史 Checkpoint 修复数据；
- 不允许测试故障注入器、环境变量、CLI 参数或模型输入在生产运行中启停安全旁路；
- 不以 monkey patch、修改 site-packages、复制 Agent Loop 或直接调用 handler 完成验收；
- 不手工改写 State/Audit/Approval/Checkpoint 来制造“恢复成功”的假象；
- 不删除失败场景、降低断言、增加默认 skip 或用额外测试替代六个必须测试文件。

## 6. 可执行契约

### 6.1 不新增生产公共 API

WP12-API-001：WP-12 不新增面向生产调用的 Harness、Gate、Sandbox、State、Audit、Approval、
Checkpoint 或 CLI 旁路接口。

WP12-API-002：测试故障能力只能通过测试模块、可信依赖注入或测试专用子进程 runner 接入；
生产配置、CLI argv、模型参数和环境变量不得选择故障点、启停注入器或改变安全判定。

WP12-API-003：正式样例必须使用现有 `load_config(path)` 严格加载，不接受仅由测试自定义解析器
认可的字段、默认值或路径格式。

WP12-API-004：最终质量门禁固定包含：

```bash
python -m pip install -e '.[dev]'
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
```

可增加目标测试和重复运行命令，但不得替代上述全量门禁。

### 6.2 最终证据

WP12-API-005：WP-12 `acceptance-report.md` 是最终验收证据的唯一汇总入口，状态只能是
`accepted`、`rejected` 或 `blocked`。只有所有 P0 场景、任务卡和质量门禁同时通过时才可为
`accepted`。

WP12-API-006：最终报告至少记录：

- 代码基线和执行日期；
- 操作系统、Python、pip、关键依赖和 `smolagents==1.26.0` 版本；
- 安装、目标测试、全量测试、lint、格式和重复运行命令及真实结果；
- 六个必须测试文件的路径、收集/通过数量和关键测试函数；
- 飞书 G/S/C/A/H/T 每项的优先级、结果、证据和归属；
- 两类任务 E2E 的 `run_id`、最终状态、验收状态、交付物、diff、测试/证据关联；
- 全部 WP12-AC 和 WP12-T 的映射；
- 失败注入矩阵与恢复判定；
- 剩余风险、未实现 P1 项、平台限制和下游影响；
- 明确声明哪些是计划、哪些由实测证明。

## 7. 行为契约

### 7.1 项目级端到端

WP12-BEH-001：代码理解任务必须由 Fake Model 驱动原生 `ToolCallingAgent`，读取真实目标文件，
提交文档写入候选，经过审批后由 Sandbox/Gate 执行，并由 Completion 根据文档结构、Evidence、
工作区 diff 和审计独立判定。

WP12-BEH-002：代码理解成功的必要事实包括：全部配置交付物存在且非空；事实引用可追溯到同一
Run 的有效读取证据；工作区源码、测试和配置未越界修改；最终 `acceptance_status=ACCEPTED`。
模型最终回答不能作为成功证据。

WP12-BEH-003：测试修复任务必须先在 Agent 产生副作用前记录失败基线、命令、工作区基线和 JUnit
证据，再允许 Agent 修复；审批后写操作经过 Gate/Sandbox；最终使用同一验收命令复跑并检查节点
守恒、当前工作区版本、diff 范围和审计。

WP12-BEH-004：测试修复在基线报告不可解析、基线无失败节点、最终退出码非 0、旧报告被复用、
基线节点丢失、新增 skip/xfail、工作区越界或结果未知时必须拒绝。

WP12-BEH-005：两类任务均通过与生产调用相同的 Harness/CLI 入口完成。测试辅助代码可以注入
Fake Model 和故障点，但不能直接调用 handler、CompletionChecker 私有逻辑或写 Gate 结果。

### 7.2 审批与恢复

WP12-BEH-006：未审批写操作首次运行必须返回 `WAITING_APPROVAL`，审批前目标文件内容、类型和
摘要不变，审批命令不执行 handler。

WP12-BEH-007：审批后的新进程 `resume` 必须重新校验配置、工作区、参数摘要、运行 ID、任务和
审批绑定，至多执行一次。再次 resume 或重复提案必须复用确定结果或拒绝，不产生第二次写入。

WP12-BEH-008：正常中断恢复后的 Step、ToolCall、预算和重复调用计数来自持久化事实，不因新
进程、新 Agent 或新模型实例清零。

WP12-BEH-009：工作区身份、HEAD/index、外围保护基线、内容摘要或审批有效期变化后，旧证据或
审批必须失效，Run 进入 `BLOCKED`/人工核对，不创建可执行 Agent 重放副作用。

WP12-BEH-010：预算耗尽固定得到 `STOPPED`、`BUDGET_EXHAUSTED`、
`NOT_EVALUATED`，不继续模型、工具或 Completion；CLI 返回非成功退出码。

### 7.3 故障注入

WP12-BEH-011：故障点必须有稳定名称，并在测试报告中记录命中的代码路径、期望持久化事实和
恢复动作。故障点未 arm 时不得改变正常行为。

WP12-BEH-012：进程崩溃场景必须在独立子进程中发生真实、不可捕获的进程退出，不能只用普通
Python 异常模拟。辅助 runner 必须把 Run ID、数据库路径、工作区和期望故障点作为受控参数传给
子进程；父测试进程在这些参数失效或路径逃逸时失败关闭。

WP12-BEH-013：审计写失败发生在允许执行或执行意图提交前时，handler 调用次数必须为 0；发生在
handler 已开始或副作用之后时，必须保留不可误判为成功的状态，不能自动重放。

WP12-BEH-014：数据库锁冲突必须在有界 busy timeout 内失败关闭或明确返回可重试状态；不得无限
阻塞、绕过锁、直接修改数据库文件或把未提交操作视为成功。

WP12-BEH-015：Checkpoint 哈希、snapshot、schema、审批关联或审计头损坏时必须拒绝恢复或验收；
不得根据损坏快照猜测执行结果。

WP12-BEH-016：租约冲突必须保证单写者语义。旧 token 不能续租、提交 Run 终态或把已经
`STARTED` 的调用重放为成功。

### 7.4 样例、文档与交付

WP12-BEH-017：两份正式样例配置必须零扩展字段通过正式 YAML/Pydantic 加载器，并覆盖各自任务
需要的工具、路径策略、预算、审批和验收字段。

WP12-BEH-018：样例若声明相对 `workspace.root` 和 `state_dir`，必须从可复现样例位置解析，
`state_dir` 位于工作区外，配置指纹稳定；不得依赖本机绝对路径或开发者私有目录。

WP12-BEH-019：`docs/test-plan.md` 必须列出 P0/P1 优先级、测试层级、离线要求、目标/全量命令、
六个必须文件、飞书场景、故障点、重复运行和证据字段。

WP12-BEH-020：`docs/operations.md` 必须覆盖配置、运行、审批、resume、inspect、状态数据库与
WAL、退出码、日志/脱敏、备份/保留、平台限制、故障人工处理、禁止操作和常见失败码。

WP12-BEH-021：根 `README.md` 必须准确描述当前实现、安装/测试入口、两类任务、安全边界、
P1 未实现项和 `docs/` 链接，不得保留过期的“仅 WP-00 完成”描述。

WP12-BEH-022：文档、配置和测试不得泄露 API Key、令牌、密码、敏感环境变量、审批 lease token
或完整未脱敏工具输出。

## 8. 故障窗口与不变量

WP12 至少验证以下故障窗口：

| 故障窗口 | 期望持久化事实 | 恢复/验收动作 |
| --- | --- | --- |
| handler 前，执行意图未提交 | 无副作用事实，审批未 claim | 可重新经过 Gate，不补记执行结果 |
| 执行意图与 claim 已提交，`STARTED` 前退出 | 调用为 `PREPARED`，审批 `CLAIMED` | 全量复核后显式 `resume_claim`，最多执行一次 |
| `STARTED` 后、handler 返回前退出 | 无法排除副作用 | 标记 `UNKNOWN_RESULT`，禁止自动重放 |
| handler 已返回、结果事务未提交 | 仍为 `STARTED` | 标记 `UNKNOWN_RESULT`，不得按工作区猜测成功 |
| 结果与审计已提交、Checkpoint 索引未提交 | 确定结果可查询 | 满足归因条件时补建 Checkpoint，不再次执行 handler |
| 结果已提交后再次同一提案 | 已有确定结果 | 返回原结果或 replay suppression，handler 不增加 |
| 允许审计写失败 | 无放行事实 | handler 调用为 0 |
| 结果审计写失败且副作用已发生 | 不得形成成功终态 | `UNKNOWN_RESULT` 或失败关闭，停止自动恢复 |
| DB 写锁冲突 | 无部分提交 | 有界失败或稳定可重试错误，不报告成功 |
| 当前 Checkpoint 损坏 | 原始损坏事实保留 | `BLOCKED`/拒绝验收，不猜测恢复 |
| 旧租约与有效租约冲突 | 单写者 fencing 事实 | 旧 token 不能提交，`STARTED` 时按未知处理 |

必须保持的不变量：

1. 拒绝、审批等待和未知结果不触达未授权 handler 或后续同批调用。
2. State、Audit、Approval 和 Checkpoint 不出现互相矛盾的“已成功”组合。
3. 已完成且结果确定的写调用最多一次物理提交。
4. 非幂等副作用结果未知时不能自动恢复成功。
5. 预算、轮数、工具调用数和时间耗用不会因新进程恢复而清零。
6. `ACCEPTED` 必须同时有当前工作区产物、有效证据和可执行 Completion 结果。
7. P0 故障注入不改变未启用测试的生产路径。

## 9. 错误与失败关闭

WP12 主要消费既有稳定错误码，不新增生产错误命名空间。最终测试或报告基础设施失败统一按以下
原则处理：

- 配置、路径、依赖或测试环境不满足：不得启动端到端任务或声明通过；
- 测试失败、未解释 skip、测试收集异常或数量异常：最终报告不得 `accepted`；
- 审计、State、Approval、Checkpoint 写入失败：按上游冻结语义拒绝或标记未知；
- 恢复结果无法唯一判定：`BLOCKED` 或 `UNKNOWN_RESULT`，不得人工改写成成功；
- 最终验收或证据汇总无法执行：WP-12 报告为 `blocked`；
- 文档与实现不一致：修复文档或回到上游工作包修复，不以“文档待办”判交付完成。

## 10. 兼容、迁移与回滚

WP12-COMPAT-001：WP-12 不新增 schema migration。需要 schema 变化时，必须回到所属上游工作包
追加 migration 并重新验收，不得在 WP-12 临时改表。

WP12-COMPAT-002：任何测试辅助接口必须使用现有 `FaultInjector` 协议或测试目录内的独立实现，
不得成为生产包导出或依赖注入默认值。

WP12-COMPAT-003：平台仍以 D-31 为准：进程执行和进程组终止只承诺 Linux/macOS；其他平台必须
失败关闭并在运维文档中明确。

WP12-COMPAT-004：回滚 WP-12 时只移除故障注入辅助、正式样例、交付文档和最终报告；不删除用户
工作区、不删除历史 State/Audit/Checkpoint，不把已完成 P0 Run 改写成未完成。

## 12. 证据与报告原则

1. 计划预期值不得复制为实测值；报告必须来自实际命令运行。
2. 每个 WP12-AC 至少映射到一个确定性测试、一个明确人工验收步骤，或明确 `NOT_RUN` 理由。
3. E2E 证据必须保留 `run_id`、最终 `RunStatus`、`acceptance_status`、相关
   `tool_call_id`/`approval_id`/`checkpoint_id` 和测试/证据摘要。
4. 拒绝路径必须提供 handler、文件或进程副作用计数为 0 的证据。
5. 崩溃恢复必须在新进程读取持久化数据库，不能复用故障子进程内存。
6. 报告记录的是只读投影和摘要，不包含完整敏感参数、密钥、审批 token 或完整模型消息。
7. P1 和未运行场景必须显式列出，不影响 P0 结论但影响“已完成能力”的表述范围。
8. 任一关键证据缺失、测试无法复跑或文档与行为冲突时，最终结论不得为 `accepted`。
